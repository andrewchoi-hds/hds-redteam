# PRD 초안 작성

아래 입력을 바탕으로 기획서 초안을 작성한다. 목적은 **완성본이 아니라 레드팀에 넣을 수 있는 검토 가능한 초안**이다.

**입력:** $ARGUMENTS

## 절차

### 1. 입력 확보

- `$ARGUMENTS`가 파일 경로면 Read한다. 여러 경로면 전부 읽는다.
- 한 줄 설명이면 그대로 쓴다.
- 아무것도 없으면 무엇을 기획할지 묻고 중단한다.

문서의 언어를 따른다(한국어 입력 → 한국어 초안).

**질문은 최대 3개까지만.** 아래 둘 중 하나라도 없으면 그것만 묻고, 나머지는 가정으로 처리한다:

- 대상 사용자가 누구인가
- 해결하려는 문제가 무엇인가

이 둘이 있으면 질문하지 말고 바로 작성한다. 부족한 나머지는 전부 `[가정]`으로 표시한다.

### 2. 구조

정확히 이 3개 섹션으로 쓴다. 섹션을 추가하거나 빼지 않는다.

```markdown
# <제품/기능명> 기획서

## 1. 개요

**배경** — 지금 무엇이 문제인가 (2~4문장)
**목표** — 이 기획이 달성하려는 것 (측정 가능하게)
**범위** — In scope / Out of scope 각각 불릿
**전제** — 성립해야 말이 되는 가정 (전부 `[가정]` 표시)

## 2. 유저 스토리

| ID | 사용자 | 스토리 | 우선순위 |
|---|---|---|---|
| US-1 | <누구> | <무엇>을 하고 싶다, <왜냐하면> | P0 |

- 스토리는 사용자 관점으로 쓴다. 기능 나열이 아니다.
- 해피패스만 쓰지 말고 실패·예외 상황의 스토리도 포함한다.
- P0(없으면 출시 불가) / P1 / P2로 구분한다.

## 3. 스토리별 요구사항

### US-1 — <스토리 한 줄>

**요구사항**
- `REQ-1.1` 시스템은 …한다.
- `REQ-1.2` 시스템은 …한다.

**수락 기준 (AC)**
- …하면 …된다.

**엣지 / 에러**
- …인 경우 …한다.

**미정** — 결정되지 않은 값 (타이머 시간, 정책, 한도 등). 없으면 "없음".
```

### 3. 작성 규칙

- **요구사항은 "시스템은 ~한다" 형태로 단일 동작만 기술한다.** 한 문장에 두 동작을 넣지 않는다.
- **AC는 참/거짓을 판정할 수 있어야 한다.** "빠르게", "적절히" 같은 표현을 쓰지 않는다. 수치가 필요한데 모르면 `REQ` 대신 **미정** 항목에 넣는다.
- **수치를 지어내지 않는다.** 타이머·한도·비율·기간처럼 정해야 하는 값은 추측해서 채우지 말고 **미정**에 남긴다.
- **입력에 없는 사실을 단정하지 않는다.** 추론해서 쓴 건 전부 `[가정]`으로 표시한다. 시장 규모·전환율·사용자 수 같은 숫자는 특히 그렇다.
- 모든 ID(`US-n`, `REQ-n.m`)는 문서 안에서 고유하고, 요구사항 ID는 소속 스토리 번호를 따른다.
- 길이보다 검토 가능성이 우선이다. 채우기 위한 서술을 넣지 않는다.

### 4. 저장

- 입력이 파일 `path/to/brief.md` → `path/to/brief-기획서.md`
- 입력이 한 줄 설명 → 현재 작업 디렉토리에 `<제품명>-기획서.md`
- 이미 있으면 뒤에 짧은 구분자를 붙인다.

### 5. 마무리 출력

저장 후 200자 이내로:

- 저장 경로
- 유저 스토리 수 / 요구사항 수
- `[가정]` 개수와 **미정** 항목 수 — 이게 레드팀이 가장 먼저 물어볼 지점이다
- 다음 단계 안내: `/redteam -prd <저장경로>`

초안의 가치는 분량이 아니라 **무엇이 아직 정해지지 않았는지가 드러나는 것**에 있다. 가정과 미정 항목을 숨기지 말고 전면에 세운다.
